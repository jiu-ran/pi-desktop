# Pi Desktop v0.9.10

这一版解决「带大图的会话打不开、打开了也很慢」，顺带把深色 / 浅色窗口配色重做了一遍，并去掉设置弹窗里一个没什么用的拖动功能。

## 症状

- 带 4K 截图的会话（单张图片 base64 约 11 MB）点开一直转圈，界面停在旧会话上，没有任何报错；会话文件越大越容易中招。
- 就算能打开，128 MB 的会话要等 **14 秒**。
- 一条消息里超过 8 MB 的图片**根本不显示**，只留一行「12 张图片」的计数。

## 原因

1. **宿主读流有 16 MB 单行上限**。宿主管道读 Pi 的 JSON-RPC 输出用的是 `bufio.Scanner`（默认 token 上限 16 MB）。带图片的消息一行就能超过这个值，`Scan()` 直接返回 `false`，读流静默中断 —— 请求永远等不到回应，表现成「会话点不开」。
2. **首屏历史白传两遍**。打开会话时宿主先调 RPC `getMessages`，Pi 把整个会话（含每张图片的 base64）序列化成一行 JSON 传回，Go 解析后整包交给 WebView；界面紧接着又从**会话文件**分页读（`messagePage`）并覆盖掉刚才那批消息。也就是说那份几十 MB 的数据只活了几百毫秒。
3. **前端 8 MB 缩略图上限**。超过上限的图片被直接丢弃，用户看不到图。

## 改法

- **读流不再有单行上限**：改用 `bufio.Reader.ReadLine` 分片拼接，长行也能完整读回来；读流意外中断时立即让挂起的请求失败（不再静默超时）；stderr 捕获上限 1 MB → 4 MB。
- **首屏直接读会话文件**：`snapshot()` 里的 `messages` 改为默认空数组，只有会话文件不存在 / 为空（刚新建）时才向 Pi 要 `getMessages`；其余交给界面按文件分页读。
- **分页里的大图改成引用**：超过 32 KB 的图片只传 `{mimeType, bytes, ref}`（`ref = 会话文件|消息序号:图片序号`），界面先画占位块，用 `IntersectionObserver` 在滚到可见（提前 240px）时调新增的 `SessionImage` 绑定取原图；点开大图时补取，同一张只取一次。后端会校验 ref 里的文件属于会话目录，不能拿来读任意文件。

## 实测

| 场景 | 改之前 | 改之后 |
| --- | --- | --- |
| 10.7 MB 会话（1 张 4K）打开 | 3.0 s | **0.11 s** |
| 128 MB 会话（12 张 4K）打开 | 14.1 s | **4.5 s** |
| 128 MB 会话的分页响应体积 | 128 MB | **3 KB** |
| 12 张缩略图 | 不显示 | 0.6 s 出第一张，4.6 s 内全部到位 |

128 MB 剩下的 4.5 秒几乎都在 Pi 自己的 `switchSession`（读那份 128 MB 的会话文件），宿主的快照与分页都是毫秒级。

## 界面

- **深色窗口配色重做**：5 套按「黑 / 灰为主 + 参考主流」重排 —— 曜石（纯黑，窗口底 `#000`）、墨玉（灰黑）、石墨（纯灰）、极光（参考 Tokyo Night）、紫檀（参考 Dracula）。底色 L* 依次 2.8 / 6.0 / 14.8 / 10.1 / 16.7，正文对比 12.0~18.0，界面原有设置会自动迁移到最接近的一套。
- **浅色窗口配色调整**：岛底从纯白改成极浅主题色，主舞台不再刺眼；表面色阶层次拉开，三级文字更清楚。
- **设置弹窗去掉「拖动边缘可移动」**：只能拖 8px 宽的边缘、没有光标提示，误触多于实用；底部只留「Esc 关闭」。
- 顺带：主题检查加了两组硬断言（文字对比度下限、表面色阶 ΔL* 层次），以后调色不会再调回糊成一团。

## 已知限制

- 剩余打开耗时主要是 Pi 自己加载会话文件，桌面端没有再优化这部分。
- 图片懒加载只在历史分页生效；刚发出的消息、工具结果里的图片仍是内联的（它们本来就新且少）。
- 滚出视口后不会卸载已加载的图片 —— 省的是打开会话的时间，不是长时间浏览的内存。
